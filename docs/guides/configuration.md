# Configuration Guide

Agent and Manager use the same YAML schema with mode-specific sections. Keep
one file per runtime user and validate it before every start or reload. See the
[field reference](../reference/configuration.md) for defaults and constraints.

## File Ownership and Validation

Production Agent configuration normally lives at
`/etc/ic-env-guard/<linux-user>.yaml`. The template unit runs as that existing
user. Its bearer token and SQLite state should be under the user's owner-only
`/var/lib/ic-env-guard/<linux-user>/` directory.

Manager configuration, bearer token, SQLite database, and credential directory
must be readable only by the existing Manager account. The credential directory
contains plaintext Agent bearer tokens: use mode `0700` for the directory and
`0600` for every credential file.

Validate without starting a listener:

```bash
ic-env-guard-config validate /etc/ic-env-guard/edaops.yaml
```

The validator checks token permissions, absolute paths, listener separation,
CIDR relationships, transport profiles, discovery bounds, and service mapping.

## Agent Configuration

This complete development example covers every main Agent subsystem. The first
two YAML examples in this guide are deliberately usable with files generated by
`./start.sh config agent` and `./start.sh config control-plane`.

```yaml
mode: agent
server:
  bind: 127.0.0.1
  port: 8765
  remote_bind_enabled: false
  trusted_lan_http:
    enabled: false
    client_cidrs: []
ingest:
  bind: 127.0.0.1
  port: 8766
  max_request_bytes: 32768
  max_concurrent_requests: 16
auth:
  mode: bearer_token
  token_file: /tmp/ic-env-guard-dev/agent.token
state_database: /tmp/ic-env-guard-dev/state.db
metrics:
  enabled: true
  collect_interval_seconds: 10
  max_observation_series: 10000
  remote_network_allowlist: []
terminal:
  idle_timeout_minutes: 60
  replay_buffer_bytes: 2097152
  exited_retention_minutes: 30
observations:
  expired_retention_seconds: 86400
  cleanup_interval_seconds: 60
logs:
  allowed_roots:
    - /var/log
    - /tmp
  max_tail_lines: 1000
  default_tail_lines: 100
  max_tail_bytes: 983040
enrollment:
  socket_path: /tmp/ic-env-guard-dev/agent-enrollment.sock
  socket_mode: "0600"
  pending_ttl_seconds: 600
  max_pending: 16
services: []
```

For production, replace `/tmp` paths with the installed paths and keep Local
Ingest on loopback. Set `server.remote_bind_enabled: true` only after selecting
an approved Public exposure policy. The Agent process runs as the selected
Linux user; service commands and Terminal sessions inherit that account's
permissions and existing sudo policy.

## Manager Configuration

This complete Manager example uses verified system TLS for Agent connections
and one bounded discovery scope. The Web-managed SQLite Registry is
authoritative; no static `agents:` list is required.

```yaml
mode: control-plane
server:
  bind: 127.0.0.1
  port: 8765
  remote_bind_enabled: false
  trusted_lan_http:
    enabled: false
    client_cidrs: []
auth:
  mode: bearer_token
  token_file: /tmp/ic-env-guard-dev/control-plane.token
control_plane:
  poll_interval_seconds: 15
  status_stale_after_seconds: 30
  max_parallel_probes: 8
  audit_database: /tmp/ic-env-guard-dev/control-plane.db
  credential_directory: /tmp/ic-env-guard-dev/manager-credentials
  max_active_terminal_proxies: 64
  max_outstanding_tickets: 128
  allowed_agent_cidrs:
    - 10.20.0.0/16
  transport_profiles: []
  discovery:
    max_concurrency: 32
    connect_timeout_ms: 500
    fingerprint_timeout_seconds: 2
    job_timeout_seconds: 120
    retention_seconds: 86400
    max_targets: 2048
    scopes:
      - id: lab-a
        name: Lab A Agents
        cidr: 10.20.30.0/24
        endpoints:
          - port: 8765
            transport_profile_id: system-tls
enrollment:
  manager_socket_path: /tmp/ic-env-guard-dev/manager-enrollment.sock
  manager_socket_mode: "0600"
  pending_ttl_seconds: 600
  max_pending: 16
  ssh_binary: /usr/bin/ssh
  ssh_connect_timeout_seconds: 10
  ssh_total_timeout_seconds: 15
services: []
```

`transport_profiles: []` still provides the reserved `system-tls` profile,
which uses the operating system trust store. Add custom CA or trusted-LAN HTTP
profiles only when required. Discovery jobs may select only named scopes from
this file; browser input cannot supply an arbitrary CIDR.

## Network Exposure and Transport Profiles

Public is the browser/API listener. It binds loopback by default. A non-loopback
bind requires `remote_bind_enabled: true`, authentication, and either normal
HTTPS termination or an explicitly configured trusted-LAN HTTP boundary.

`server.trusted_lan_http` constrains clients reaching this runtime's Public
listener. `control_plane.transport_profiles` independently constrains Manager
connections to Agents:

- `verified_tls` verifies the Agent certificate with the system trust store or
  an owner-safe CA bundle.
- `trusted_lan_http` permits plain HTTP only to private CIDRs explicitly listed
  in the profile and covered by `allowed_agent_cidrs`.

Loopback HTTP Agents are development-only and require
`development.allow_insecure_http: true` on a loopback-only Manager. Never use
that setting to weaken non-loopback Agent verification.

Local Ingest is different: its bind accepts only `127.0.0.1` or `::1`, carries
no bearer token, and must not be proxied, port-forwarded, or exposed remotely.

## Services, Logs, and Observations

Each service must map to exactly one execution source: `command` or
`systemd_unit`. The allowlist of operations is mandatory. Example command
mapping:

```yaml
services:
  - id: demo-http
    name: Demo HTTP service
    command: python3 -m http.server 18080
    cwd: /tmp
    allowed_operations: [start, stop, restart, status, healthcheck]
    restart: never
    healthcheck:
      type: tcp
      target: 127.0.0.1:18080
      interval_seconds: 10
      timeout_seconds: 2
      failure_threshold: 3
    logs:
      capture: true
      max_tail_lines: 200
```

For an existing unit, replace `command` with a full `.service` name such as
`my-worker.service`. Do not configure both.

Local producers publish only the latest Observation and Log Source metadata.
The `observations` section controls expired-row cleanup. The `logs` section
restricts tail reads to absolute roots and bounds both requested lines and
returned bytes. Log content is read on demand and is never stored in SQLite.

## Enrollment Configuration

An Agent exposes an owner-controlled Unix socket used by the fixed SSH
enrollment helper. A Manager can expose a separate local Unix socket for the
`ic-env-guardctl` orchestration path. Socket mode is `0600` for one runtime user
or `0660` only when a deliberate primary-GID policy is configured.

Pending credentials expire in 60–900 seconds and are one-use. The SSH total
timeout must cover the connection timeout. For non-interactive service-key
operation, configure both `service_key_identity_file` and
`service_key_known_hosts_file`; configuring only one is invalid.

Enrollment uses existing accounts and normal SSH host-key verification. It does
not create an Agent account, distribute private keys through HTTP, or modify
sudoers.

## Validate Before Restarting

```bash
sudo ic-env-guard-config validate /etc/ic-env-guard/edaops.yaml
sudo systemctl restart ic-env-guard@edaops.service
curl --fail http://127.0.0.1:8765/healthz
curl --fail http://127.0.0.1:8765/readyz
```

If validation fails, fix the reported field instead of bypassing it. After a
Manager change, probe one Agent and confirm its identity/capability state. After
an Agent change, verify Public and Local Ingest are on different ports and that
Local Ingest remains loopback-only.
